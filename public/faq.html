Documentation & FAQ

How it works, and the usual questions.

Everything below follows from one design choice: the files never reach a server.

What it is

Two browsers, one direct line.

Aurora FileShare sends files straight from one browser to another. There is no upload step and no copy sitting on a server afterwards — the two browsers form a direct, encrypted connection and the bytes flow across it.

That single design choice is where most of the behaviour below comes from: there is no size limit because there is nothing to store, and the sender has to keep their tab open because their device is the source.

How a transfer works

Four steps, and the server is only in the middle two.

01

You pick files

They stay on your device. Nothing is read or copied yet.

02

You get a link

It ends in a random secret after the #, which your browser never sends to us. The file names are encrypted with it.

03

They open the link

The server introduces the two browsers to each other — this is called signalling — and then steps out of the way.

04

Direct and encrypted

The browsers connect over WebRTC and the file streams across, encrypted end to end by DTLS.

The server never receives, stores, or relays file contents. It cannot: the bytes travel on a connection it is not part of.

What the server sees

Enough to make the introduction. Not enough to read anything.

The server knows that a share exists, how many files it has and how large they are, and which addresses connect to it. The file list is encrypted with a secret it never receives, and the contents never pass through it at all.

FAQ

Everything people ask.

Is there a file size limit?

No. Because nothing is uploaded, there is no storage quota to hit. Transfers are streamed in small chunks and written straight to disk, so a 50 GB file uses no more memory than a 5 MB one. The practical limits are your connection speed and the recipient's free disk space.

Where are my files stored?

Nowhere. There is no bucket, no disk, no temporary copy. When the transfer finishes, the only copies that exist are the sender's original and the recipient's download.

Can I send more than one file?

Yes, up to 64 at a time. The recipient can take them individually, or download the whole set as a single .zip. The archive is assembled as the bytes arrive rather than built up first, so it starts saving immediately and never has to fit in memory.

What does the server actually see?

Being precise, because "nothing" would be an overstatement: to introduce the two browsers, the server briefly holds how many files a share has and how large they are, plus an encrypted copy of the file list that it cannot read. The connection details the two browsers exchange pass through it encrypted as well. It also sees the IP addresses connecting to it, as any web server does — and so does Cloudflare, which the site runs behind — and uses them to limit how often shares can be created and wrong links tried. None of this is written to disk, and all of it disappears when the share ends.

Search engine crawlers are recorded by name — that Googlebot visited, and which page it asked for — so we can tell whether the site is being indexed. No address is stored with it, and ordinary visits are not recorded at all.

To know whether anyone uses it, the server counts two numbers per day: how many shares were created and how many recipients connected. Nothing is attached to those counts — no address, no link, no file name or size — and each day's totals are written down only once that day is over, so they say nothing about who used it or when.

What it never sees is file contents.

Is the transfer encrypted?

Yes, and not optionally. WebRTC data channels are encrypted with DTLS as part of the protocol — there is no mode in which the data crosses the network in the clear.

It is also encrypted against us. The secret after the # in every link never reaches our server, and the file list and everything the two browsers say to each other while connecting are encrypted with it. So neither we, nor anyone who took over our server, could read your file names or slip in between the two browsers.

Can someone guess my link?

No. The words at the start of a link are only a label; what opens the share is the random 128-bit secret after the #, and guessing that is not realistic. The server also cuts off anyone who keeps trying wrong links. If you worry the link itself might leak, tick "Ask me before each person connects": nobody sees anything, not even the file names, until you let them in.

Can I password-protect a share?

Yes. Set a password when you create the link and recipients must enter it before they can even see the file list. Send the password separately from the link — a password in the same message protects nothing. After ten wrong passwords the share closes itself.

How do I report misuse?

Send the share link and what is wrong with it to . If the share is still live we close it, which also stops a transfer in progress. We cannot see what was sent, so we cannot check the contents ourselves; the terms of use say what is not allowed.

What if the connection drops half way?

The transfer picks up where it stopped. If the direct connection between the two browsers breaks — Wi-Fi drops, a laptop switches networks, a router restarts — both pages keep trying to reconnect for up to ten minutes, and the download continues from the last byte that arrived instead of starting over. That works for single files and for a ZIP of several. A hiccup on our server does not interrupt a transfer at all, because the files never pass through it.

What cannot be resumed is a closed tab or a reloaded page on either side: the sender's browser is the only copy of the files, and a download the browser has given up on cannot be continued. Then it starts from the beginning.

The recipient cannot connect. What went wrong?

Almost always restrictive networks on both ends. A direct connection needs at least one side to be reachable, and some corporate and mobile networks prevent that in a way that cannot be worked around from the browser. If both sides are on such a network, no direct route exists and the transfer cannot start.

Switching either end to a different network — a home connection, or a phone's hotspot — is usually enough.

How long does a link last?

Until you close the tab, or four hours of inactivity, whichever comes first. Links are not meant to be permanent — for anything long-lived you want actual hosting, not a peer-to-peer transfer.

Do I have to keep the tab open?

Yes. Your browser is serving the file, so closing the tab ends the share the same way unplugging a server would. Recipients who are mid-download are told the share has ended.

Can several people download the same share?

Yes. Each recipient gets their own direct connection to you, and you can watch their progress individually. Bear in mind you are uploading to each of them separately, so ten recipients means ten times the upload.

Which browsers work?

Any current version of Chrome, Edge, Firefox, Safari or their mobile equivalents. On browsers that support it, downloads stream directly to disk; elsewhere the file is assembled in memory first, which the page will tell you, and which makes very large files unreliable.

Is it free?

Yes, with no account and no limits. It costs very little to run precisely because the files never touch the server. If it saved you a trip to a file-hosting site, there is a tip button in the header.

Can I run it myself?

Yes — it is a small self-contained Node application and self-hosting is a reasonable thing to want for something handling your files.
